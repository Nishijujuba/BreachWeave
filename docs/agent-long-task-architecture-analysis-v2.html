控制平面任务拆分

Challenge Manager：把长程任务切成可调度单元

Manager 像调度塔台，负责题目实例、solver 槽位、planner prompt、上一轮动作和资源约束。

它的核心价值是把“下一步派谁做什么”变成一个稳定的资源调度问题。planner snapshot 汇总未完成题目、活跃 solver、stale 状态和 prompt 统计，减少模型凭短期情绪频繁换线。

亮点

  • 用 `MAX_ACTIVE_CHALLENGES` 和 `maxSolvers` 给探索并发设硬边界。
  • 记录上一轮 planner digest，压低重复启动、重复停止、重复改阵型的概率。

关键函数

  • tickPlanner：防重入并按配置触发调度。
  • buildPlannerSnapshot：把题目、solver、prompt 和统计压成 planner 输入。
  • createPlannerTools：把启动、停止、查状态封成 planner 可调用工具。

结束判定外部状态

Challenge Store：用 flag 进度判断任务是否结束

结束判定落在 store 的权威状态上，solver 的自我判断只作为过程信号。

长程 agent 容易提前停止，尤其在拿到一个 flag 之后。这里用 `flag_count` 和 `flag_got_count` 定义完成条件，相当于把终止条件从主观叙述转到外部记账。

亮点

  • 完成条件很窄，只有已知 flag 总数大于 0 且获取数达标才算完成。
  • Ralph-loop 和 host bridge 都复用同一个 store 判断，减少多处口径漂移。

关键函数

  • computeChallengeCompleted：纯函数完成判定。
  • isChallengeCompletedInStore：从持久化记录读取后复用判定。

会话组装固定与自由度

Solver Session：把 prompt、workspace、extension 组装成执行上下文

Session 层是 agent 进入任务世界的入口，它决定模型能看见什么、在哪写文件、会被哪些 extension 约束。

`createSolverSession` 读取 prompt 配置，建立 solver 目录和 workspace，并把 observer extension 绑定到会话中。注释掉的 extension 也很有信息量：它们显示系统已经预留大输出降噪、scope guard、RTK rewrite 等控制点。

亮点

  • 启动快照写入 `startup.json`，为复盘和统计保留 session 配置。
  • observer 模型可从 prompt meta 单独指定，监督者和执行者可以使用不同模型。

关键函数

  • createSolverSession：构造 solver 主会话。
  • createSubagentSession：构造共享 workspace 的子 agent 会话。

执行平面JSONL 事件流

Runtime Manager：容器执行、事件回流、host bridge 转发

Runtime 是真实执行层，负责把 solver 跑进 Docker，并把 stdout JSONL 转成系统事件。

这一层让模型动作可观察：容器启动、会话目录、workspace、host bridge 请求、tool result 和 agent_end 都进入统一事件流。长程任务的复盘能力很大程度来自这里。

亮点

  • solver 状态、进程、环境变量、live message 分开记录，降低状态缠绕。
  • JSONL 流里遇到 host bridge 请求会转发给宿主处理，再把响应送回 solver。

关键函数

  • launch：启动 solver 容器并注入 runtime/workspace。
  • readStream：读取 stdout，解析 JSONL 事件。
  • getDetails：聚合 main、subagent、observer 线程。

监督平面漂移监测

Observer Loop：把执行轨迹切成可审计窗口

Observer loop 监听主 agent 事件，把工具调用、结果摘要、assistant message 汇成 review payload。

它的定位很克制：只做旁路观察、排队 review、必要时发纠偏提醒。这样主 solver 保持执行权，observer 保持审计权，职责边界清楚。

亮点

  • review 队列串行 drain，避免多个 observer review 同时改看板。
  • 纠偏提醒经过去重和完成状态检查，减少无效打断。

关键函数

  • buildObserverPayload：组装 review 输入。
  • attachObserverLoop：绑定事件监听和 review 队列。

监督者看板维护

Observer Agent：维护 idea/memory，看见漂移时轻量纠偏

Observer agent 读取最近 rounds 和 challenge 状态，更新策略看板与 durable memory。

它的设计重点是降低上下文腐烂：把有价值事实沉淀到 memory，把待验证路线留在 idea，把低价值流水账排除在外。数学上可以理解为把原始上下文 \(C\) 投影到高信号状态 \(S=(M,I,R)\)。

亮点

  • review 前先查询 `challenge_get_state`，题目完成后直接跳过。
  • observer session 独立放在 `.observer`，监督轨迹可以单独复盘。

关键函数

  • buildObserverPrompt：构造审计输入。
  • runSolverObserverReview：运行 observer agent。
  • observer-store：持久化队列和 rounds。

续跑循环早停治理

Ralph-loop：agent 结束后仍用外部状态决定是否续跑

Ralph-loop 监听 `agent_end`，题目未完成时注入 continuation message 触发下一轮。

这个模块专门处理“阶段性停顿被误当成终局”的问题。若上轮错误退出，它用指数退避控制重试；若题目未完成，它触发下一 turn，让 solver 在已有上下文上继续推进。

亮点

  • 续跑由 `challenge_is_completed` 驱动，避免 solver 自我早停。
  • 错误重试有上限和退避，防止无限错误循环。

关键函数

  • isChallengeCompletedByHostBridge：查询权威完成状态。
  • attachChallengeContinuation：绑定 agent_end 并触发续跑。

状态平面记忆管理

Idea / Memory Store：把假设和事实分层保存

Idea 是待验证攻击路线，Memory 是耐压缩事实、证据、失败边界、hint 和约束。

这层是对抗上下文腐烂的关键。Idea 像白板，允许被推进、验证、跳过；Memory 像证据柜，要求可复用、可引用、可跨轮保存。

亮点

  • Idea 通过归一化文本做去重，降低同义路线反复出现。
  • Memory 每条都有 `kind`、`refs`、`source`，利于压缩后继续追证据。

关键函数

  • appendChallengeMemory：写 durable memory。
  • addChallengeIdea：新增或复用 idea。
  • updateChallengeIdea：推进 idea 生命周期。

通讯层协作同步

Host Bridge：把 solver 请求接到宿主权威状态

Host bridge 处理状态查询、hint、flag 提交、memory/idea 更新，并向同题 solver 广播。

它像一个裁判兼广播台。solver 可以请求宿主状态，宿主可以把正确 flag、hint、看板更新同步给其他 solver，减少并行 agent 的重复劳动。

亮点

  • flag 提交附带 solver、prompt、model 和 writeup 元数据。
  • 正确提交后向同题 solver 同步剩余 flag 和路线摘要。

关键函数

  • formatFlagSolvedBroadcastMessage：生成同题广播。
  • handleChallengeAction：分发 challenge action。
  • createChallengeHostBridgeHandler：暴露宿主处理器。

Large Tool Result：大输出落盘，只把定位信息放回上下文

大工具结果容易淹没推理，extension 把完整内容写入 `.tool-results`，上下文只保留摘要和路径。

这相当于给上下文加了“外部存储层”。模型保留索引和预览，需要细节时再读取文件，避免每次 turn 都携带大段低密度文本。

亮点

  • 按 `maxInlineChars` 触发 spill，默认路径稳定。
  • 返回内容包含 `type=large_tool_result_spill`、原始字符数和相对路径。

关键函数

  • serializeContentBlocks：序列化 tool result。
  • largeToolResultExtension：监听并落盘大输出。

复盘层可观测性

Attack Timeline / Stats：把长程执行变成可复盘数据

Timeline 串起 attempt、submission、solver、observer、memory 和 idea 事件；stats 汇总 token、耗时和解题质量。

长程 agent 系统需要能解释“为什么成功或失败”。时间轴给过程复盘，统计给策略调参，两者共同支撑 prompt、模型、调度策略的迭代。

亮点

  • 事件按 lane 分类，challenge、submission、solver、observer 可以分轨查看。
  • stats 读取 session usage，能把成本与解题表现关联起来。

关键函数

  • buildChallengeAttackTimeline：构建复盘时间轴。
  • refreshChallengeStats：刷新题目和 solver 统计。
  • buildChallengeStatsOverview：生成全局统计概览。
